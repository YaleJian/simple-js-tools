# 方法设计与贡献规范

## 新增方法前的评审

每个新方法都必须先回答：

1. 是否解决了真实且重复出现的问题？
2. 原生 JavaScript、DOM 或 Node.js API 是否已经足够简洁？
3. 现有模块是否已有相同或高度重叠的能力？
4. 它是可复用工具，还是只适合某个业务的便捷函数？
5. 名称、参数、返回值和异常行为是否容易预测？
6. 边界条件和运行环境是否可以明确说明？

存在原生等价 API、仅减少一两行代码或无法给出稳定语义时，默认不新增。

## 模块归属

- `compare`：无副作用的值类型与特征判断。
- `object`：通用对象数据处理。
- `xhr`：浏览器 XMLHttpRequest 的模拟与劫持。
- 新领域必须具备多个相互关联且必要的方法后再建立新模块，不创建空模块占位。

## 实现要求

- 优先使用标准 API，避免引入运行时依赖。
- 保持一个方法只承担一个清晰职责。
- 不修改全局对象或原型，除非模块的公开目的就是 Hook，且文档明确风险。
- 对安全边界、兼容行为和反直觉逻辑添加中文注释；不逐行翻译代码。
- 不静默吞掉无法恢复的错误。

## 完成条件

新增或修改公开方法必须同时完成：

- 在对应 `docs/<module>.md` 中记录参数、返回值、示例、限制和异常。
- 添加正常路径、边界条件与错误路径的单元测试。
- 运行 `npm test`。
- 运行 `npm run build`，确认 ESM、CJS、IIFE、UMD 产物成功生成。
- 检查入口和文档中没有残留无效模块或过期方法。
